Concurrent irregular host-queue chunk control, M4 Pro, 2026-08-07
=====================================================================

This is an honest irregular concurrent chunk control, NOT live ingress into one
persistent resident command buffer. The current API freezes each chunk before
its independent submission and exposes no device-visible ingress ring.

Example: examples/resident_dynamic_irregular_arrival.rs

Eight host threads each construct their own Metal backend/pipelines, synchronize
at a ready barrier, then a second barrier releases them against a shared
OnceLock<Instant>. Setup/compile is excluded. Delays after release are
[0,3,11,12,24,31,33,45] ms and frozen lane chunks are
[8192,4096,12288,2048,16384,6144,10240,6144]. Calls overlap (observed peak
in-flight 2--3 grouped and exactly 3 generic) and completion order differs from
launch order. Each full measurement therefore has eight real command-buffer
submissions on independent queues, not eight sequential calls.

The 65,536 total lanes retain alternating A/B layout, interleaved depth, 16
steps, WORK=512 and competent generic break_if. Two AB/BA batches of 11 samples
all match exact complete frames and globally rebased/sorted canonical trace.
Elapsed time begins at simultaneous release and includes scheduled arrival waits,
per-call allocation, encoding, submit/wait/readback, and thread join.

This control establishes the concurrent irregular workload but no stable
performance direction: position-stratified batch G/generic ratios are 1.0287
and 0.9889 (a reversal). Overall median makespans are 54.108 ms grouped and
53.634 ms generic. It is descriptive negative evidence only and does not meet
the requested resident asynchronous-arrival application semantics.
